# What Stageproof does and does not do

Last updated: 2026-11-23.

This page is the scope of the command line tool.

## The job, in one paragraph

Stageproof looks at a pull request that changes a Helm chart and says whether that upgrade is safe to merge. The chart might live in the repository, an Argo CD Application might name the chart and the version, or a Flux HelmRelease might. It can also compare two sets of rendered manifests, and two versions of a chart in a Helm repository or an OCI registry. The released binary is v0.3.1. The tool compares the version you run now with the version the pull request wants, using the values you actually set and the Kubernetes version you say the cluster runs. It prints one result and exits 0, 1, or 2. `stageproof explain <rule-id>` prints the level, the meaning, and what to do for one rule, and exits 2 when the id is not a rule. The job log and the Markdown comment list Deletes, CRDs, Privilege, Exposure, Values, Restarts, and Not checked before the check list, and leave out an empty section. `--format sarif` prints one SARIF 2.1.0 log. `--format json` and `--out` match `docs/report.schema.json`. `check-pr` reads `.stageproof.yaml` from the base ref. An ignore on that file keeps the finding in the report and stops it from blocking. An ignore added only in the pull request does not. `check` and `check-pr` do not edit the pull request. `stageproof comment` posts or updates one comment from the Markdown file you pass, and it does not merge the pull request. Nothing in the tool changes a cluster you already have. `stageproof mcp` serves `check`, `check_pr`, and `explain` on stdin and stdout for a directory you name with `--root`. It does not open a port, write a file, or start a live rehearsal.

## Two different upgrades

People say "Kubernetes update" for two different jobs. Stageproof only does the first one, and it uses the second as a fact you tell it.

| Upgrade | Example | What Stageproof does |
|---|---|---|
| Application upgrade. A Helm chart, the chart version an Argo CD Application points at, or the chart a Flux HelmRelease points at, moves to a newer release. | argo-cd chart 10.9.6 to 10.18.0. Redis image tag inside a chart. | This is the product. Stageproof compares the old release with the new one. |
| Cluster upgrade. The Kubernetes control plane and nodes move to a newer minor version. | The cluster moves from 1.35 to 1.36. | Stageproof does not upgrade a cluster, does not drain nodes, and does not check kubelet skew, PodDisruptionBudgets, or add-on compatibility for the platform itself. You pass `--current-k8s 1.35` and, if you want, `--next-k8s 1.36`. It then asks whether the chart you are upgrading still renders objects that those Kubernetes versions accept. |

`--current-k8s` is the version the cluster runs today. A chart that uses an API that version has already removed is `BLOCKED`. `--next-k8s` is the version you plan to move the cluster to later. An API that still works today but is removed in that next version is a warning, not a block. The pull request can merge. You have been told the cluster upgrade will break that object later.

`--live` does not rehearse a cluster upgrade. It starts a temporary empty kind cluster at the current Kubernetes version, installs the old chart, upgrades to the new chart, runs the `smoke` commands from `.stageproof.yaml`, rolls back, and deletes that temporary cluster. `check-pr` reads that list from the base ref. A command added only in the pull request does not run. The cluster you deploy to is never contacted.

`--live` starts a real Kubernetes node. That node is a container, and it has to set up its own networking and start more containers. An unprivileged container is blocked from doing those things, so kind has nothing to run the node with. A CI job that cannot start containers stays on the file check.

## Argo CD and Flux

Argo CD and Flux are both in the released binary, v0.3.1.

Both tools are ways to write down "this Helm chart, this version, these values." The check behind them is the same chart upgrade. A Flux file is not a second product.

| Input | Now | Later, same check | Not the job |
|---|---|---|---|
| Helm chart in a directory, with your values files | Yes. `stageproof check --current-chart` and `--new-chart`. | | |
| Two versions of one chart in a Helm repository or an OCI registry | Yes. `stageproof check --repo <url> --chart <name> --from <version> --to <version>`. Stageproof runs `helm pull` and deletes the temporary directories. A failed download is NOT CHECKED. Without `--repo`, `--chart`, `--from`, and `--to` are still directory aliases. | | |
| Argo CD Application. One Helm chart, from a chart repository (`repoURL` and `chart`, including `oci://`) or from a directory in this checkout. Several sources, `valueFiles`, `valuesObject`, `parameters`, and `releaseName` are read. A `.yaml.tmpl` is accepted. `${...}` placeholders are replaced with fixed samples so the file parses. | Yes. `stageproof check --argocd-file`. `check-pr` also follows a values file the Application names. An ApplicationSet, a chart or `$ref` values file in a different Git repository, a `ref` source that also sets `path`, and `sourceHydrator` are NOT CHECKED. Stageproof does not clone them and does not render chart defaults in their place. | | |
| Pull request or merge request | Yes. `stageproof check-pr` reads `git diff` and checks every changed chart, every changed Argo CD Application, and every changed Flux HelmRelease. A file deleted inside a chart is still a change to that chart. A source object, a `valuesFrom` file, or a file under a chart path the HelmRelease names is part of that check. It does not call Renovate, GitHub, or GitLab to ask what changed. | | |
| Flux `HelmRelease` | Yes. `stageproof check --flux-file`. API versions `helm.toolkit.fluxcd.io/v2`, `v2beta2`, and `v2beta1`. `spec.chart.spec` resolves a HelmRepository, an OCIRepository, or a GitRepository in this repository. `spec.chartRef` resolves an OCIRepository or a HelmChart in this repository. `spec.values` and `spec.valuesFrom` are read. A missing `valuesFrom` object is a warning, the chart is still rendered, and the result stays `PASSED`. `spec.upgrade.crds` is read. Omitted means Skip. A GitRepository on another host, `ExternalArtifact`, a Bucket, both chart fields, and a missing chart `valuesFiles` entry are NOT CHECKED. Stageproof does not clone them and does not render chart defaults in their place. | | |
| Rendered YAML manifests | Yes. `stageproof check --before` and `--after` read a `.yaml` or `.yml` file, or a directory of them. Chart stages are skipped. The API server, the impact check, and the API table run. `--live` with these flags is exit 2. `check-pr` still ignores a loose manifest that is not inside a chart. | | |
| Kustomize, Helmfile | No. The files are ignored. | | |
| Terraform providers, modules, and plans | No. | | A provider or module version change is not a Helm upgrade. |
| Container image contents (base image, libc, user, entrypoint) | The contents are not inspected. A new or changed tag is asked of the registry named in the render, with HTTP HEAD. A manifest list is read only to see whether linux/amd64 is present. `--cluster-facts` replaces that pair with the operating system and architecture of each node in the file. No nodes leaves linux/amd64. `--offline` skips that and does not change `--api-server`. A 401, a 403, a timeout, or a rate limit is not a block. A missing tag is `BLOCKED`. | | Deciding whether a new base image is safe to run. |
| Language packages (npm, Maven, Go modules, and the rest) | No. | No. | Renovate already has Merge Confidence for those. |
| Kubernetes cluster upgrade itself | No. See the table above. `stageproof facts export` reads the server version, custom resource definitions, admission policies, StorageClass names, and installed chart versions from a kubeconfig you pass. The calls are get and list. The default role does not include Secrets. `--helm-releases` also needs `deploy/facts-helm-releases-clusterrole.yaml`. `--cluster-facts` uses that file when `--current-k8s` is not set. Stageproof still does not perform the upgrade. | | Drains, skew, control-plane add-ons, and "click upgrade" on EKS, GKE, or AKS. |

## What the check looks at today

| Question | Answered now? | How | What it does not prove |
|---|---|---|---|
| Does the new chart render with your values? | Yes | `helm template` on Helm 3 or Helm 4. For an upgrade check, the current chart renders in install mode and the new chart renders with `--is-upgrade`. If `--is-upgrade` fails while install mode succeeds, Stageproof falls back to install mode and emits `helm.template.upgrade_fallback`. `--helm-compare` renders again with a second helm binary and reports `helm4.render_differs` when the parsed objects differ. A field that changes between two renders of the same binary is ignored. When the current chart does not render because a default is empty, a schema field is null, the schema document is invalid, or a template names a missing API, the same placeholder is used on both charts and the report names the keys. A value you set is not replaced. A failure that appears only on the new chart stays a blocker. | That the rendered objects are the ones you wanted. A post-renderer, a registry login URL, and a renamed Helm flag are not visible in the chart. |
| Does every key in your values file still do something? | Yes, for keys the reader cannot decide | A template that reads an exact path, and a key listed in the chart `values.yaml` or `values.schema.json`, stays `"proof": "templates"`. A wildcard, a `toYaml`, or a merge is rendered twice: once without the key, and once with another value of the same type when your value matches the default. A YAML list is one key. Fields that change between two identical renders are ignored. A key with an effect in the old chart and none in the new chart is `BLOCKED` (`helm.values.silently_dropped`, `"proof": "render"`). A schema rejection of that probe is not a finding. `--values-proof full` render-tests every key. A chart default you do not set is `helm.values.default_changed` when the old default still changes the render. A matching effect on a new key is `helm.values.renamed` with `"verified": true`. The report names keys and chart defaults. It does not print your values. Argo CD `helm.parameters` and `--set` are included as a values file. | A key read by an exact path is not rendered again unless you pass `--values-proof full`. A probe that `values.schema.json` rejects is not proof that the key is unused. More than eight changed defaults in the default mode are one warning, not one proof per key. |
| Did the chart version, appVersion, image ref, or a Chart.yaml dependency change? | Yes, as a warning | The report names a minor-version skip, a new major, a changed `appVersion`, a changed container image, and a dependency constraint whose packaged chart under `charts/` did not change. A tag that only gains or loses a leading `v` is called out. A new or changed tag is also asked of its registry. An unchanged tag is not. `apiVersion: v3` in the new `Chart.yaml` is `helm4.chart_v3`. | That the upstream project forbids the skip. A 401, a 403, a timeout, or a rate limit is not proof the tag is missing. Charts v3 are experimental. |
| Does the chart use an API your Kubernetes version has removed? | Yes | `--current-k8s` starts a local API server of that minor (`--api-server auto`), reads its discovery, and passes every served `group/version` and `group/version/Kind` to `helm template` via `--api-versions`. A kind the server does not serve is `BLOCKED`. If the binaries cannot be downloaded or `--api-server off` is set, the embedded discovery table for `1.34` to `1.37` supplies `--api-versions` and the built-in removal table checks the rendered objects. `--api-server require` is `NOT CHECKED` when the binaries are missing. `--cluster-facts` sets the minor from the exported server version when `--current-k8s` is not set, and installs those custom resource definitions on that local server. | The patch that ran is named in `checked:`. It is not a claim that your cluster is that patch. Deprecations still come from the table. `helm template` includes legacy API versions in its built-in capability list and cannot remove them; when a template guards an object on `.Capabilities.APIVersions` for a removed API version, that finding is downgraded to a warning because the removal is not proven. |
| Will the next Kubernetes version remove an API the chart still uses? | Yes, as a warning | `--next-k8s` dry-runs the new objects as creates on a second local API server when that minor is published. Otherwise the table is used. | It does not block the chart upgrade. It does not upgrade the cluster. |
| Can the upgrade be applied on top of the old release? | Partly | The local API server applies the current objects and dry-runs the new ones. An immutable field, including a Job pod template and a StatefulSet `volumeClaimTemplates` change, is `BLOCKED`. A label selector change is still `BLOCKED`. A Helm hook is dry-run as a create. When an object's template uses `.Release.Revision` in a dynamic name, an immutable-field rejection is downgraded to a warning because `helm template` always renders revision 1 while `helm upgrade` creates a new name. An unknown field is a warning with client-side Helm and `BLOCKED` with server-side apply. A new Helm 4 install is server-side apply. An upgrade of a release Helm 3 created stays a warning unless `--server-side-apply` is set. An unsupported enum value is `BLOCKED`. A Helm hook is not reported as a delete or a restart. CRDs larger than 256 KiB are a warning. The same run compares the two object sets for deletes, restarts, exposure, privilege, capacity, and CRD schema changes. When the API server did not run, that check says the comparison used the rendered objects. | A templated CRD, a PersistentVolumeClaim, or a Namespace that the new chart drops is `BLOCKED`, unless the object has `helm.sh/resource-policy: keep`. A StatefulSet delete is `BLOCKED` only when `persistentVolumeClaimRetentionPolicy.whenDeleted` is `Delete`. A CRD scope change, a removed storage version, or a field change that an existing custom resource of that version uses is `BLOCKED`. A newly required field the object already sets, and an enum value that is still allowed, are warnings. Other schema changes are a warning. An incompatible change to a CRD under `crds/` is `BLOCKED`, because plain Helm does not upgrade that directory. A Flux HelmRelease uses `spec.upgrade.crds`. Omitted and Skip are that same block. Create warns. CreateReplace is info. The helm-controller type comment says the upgrade default is Skip. The user guide lists Create as the default for both install and upgrade. This check follows the type comment. A restart, a lower replica count, and a higher resource request are info. The report does not print values. An API server proof without `--live` is still `PASSED`. |
| Does the new release start, and can you roll it back? | Only if you pass `--live` | Temporary kind cluster on the machine running the command. Each step waits up to 10 minutes. Install, upgrade, the `smoke` commands from the base `.stageproof.yaml`, roll back, delete. If the current chart misses the deadline and the release is still there, the next step upgrades that release with the same values. A fresh install of the new chart is only used when there is no release to upgrade, and it is not called an upgrade. The deadline is reported as `context deadline exceeded`. A call to the cluster's own API is not an outside service. | Your real data, traffic, secrets, and private images. A slow empty-cluster install is not a broken chart. |

## What a result means

| Result | Exit | Human reading |
|---|---|---|
| `PROVEN` | 0 | The files passed, and the temporary cluster installed the old chart, upgraded, and rolled back. |
| `PASSED` | 0 | The files passed. When no rehearsal ran, the job log prints `NOT TESTED LIVE` in red and the comment repeats that sentence. Exit 0 means the pipeline is not blocked. It does not mean the upgrade was rehearsed. |
| `BLOCKED` | 1 | The upgrade has a problem the report names. CI should fail. |
| `NOT CHECKED` | 2 | Stageproof did not finish, or `--require-rehearsal` was set and no upgrade rehearsal passed. CI should fail. This does not mean the upgrade is unsafe. A file check that did not rehearse stays `PASSED` and says it was not tested live. |

A live rehearsal is `--live` on the runner that runs the command. `v0.3.1` does not read a saved rehearsal report. The previous release, v0.1.8, still accepts `--saved-live`.

Measured accuracy across 12 active incidents and 316 CNCF upgrade pairs (105 CNCF projects) is in [docs/accuracy.md](accuracy.md).
