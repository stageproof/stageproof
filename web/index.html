01 Zero setup

One binary scans any upgrade in seconds.

You do not need a staging cluster, a kubeconfig, or an account. Install the binary and run your first check.

Step 1 · Install

One free binary

Install via Homebrew, as a Helm plugin, with Docker, or grab a signed Linux, macOS, or Windows binary from GitHub Releases.

Step 2 · Run

Point at any upgrade

Give it a public chart repo, two local folders, a git pull request, an Argo CD Application, a Flux HelmRelease, or rendered YAML.

Step 3 · Decide

Read the verdict

A local Kubernetes API server for your version tries the upgrade. The exit code is 0 when it passes, 1 when it is blocked, and 2 when it could not be checked.

Downloads both versions of a public chart and compares them on your machine. Nothing is installed in a cluster.

Replace values.yaml with the values file you deploy. Remove the last line to use the chart's own defaults.

stageproof check \
  --repo https://kubernetes-sigs.github.io/metrics-server/ \
  --chart metrics-server \
  --from 3.12.2 --to 3.13.0 \
  --current-k8s 1.35 \
  -f values.yaml

Run this in your git checkout. It compares your branch with origin/main and checks every Helm chart, Argo CD Application, and Flux HelmRelease that changed. It does not contact your cluster.

--current-k8s is the Kubernetes version you run. --next-k8s also warns about APIs the next version removes.

A chart is checked with its own values.yaml. To check the values files you deploy, list them in .stageproof.yaml. stageproof init writes that file for you. Argo CD and Flux use the values files their manifests already name.

stageproof check-pr \
  --current-git origin/main \
  --current-k8s 1.35 \
  --next-k8s 1.36

Save this as .github/workflows/stageproof.yml. It runs the same pull request check on every pull request and posts one comment with the result.

Set current-k8s to the Kubernetes version you deploy to. Values files follow the same rule as the pull request check. Use the pull_request trigger, not pull_request_target.

name: stageproof
on:
  pull_request:
permissions:
  contents: read
  pull-requests: write
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: stageproof/action@v1
        with:
          current-k8s: "1.35"

Add this to .gitlab-ci.yml. It runs the same pull request check on every merge request.

Set current_k8s to the Kubernetes version you deploy to. To get a comment on the merge request, add a STAGEPROOF_GITLAB_TOKEN CI variable, because CI_JOB_TOKEN cannot write comments. Without it, the report is saved as a job artifact.

include:
  - component: gitlab.com/zarovvvv/stageproof/stageproof@1
    inputs:
      current_k8s: "1.35"

Add this to your Renovate config. Each Helm update pull request then shows a badge with the chart index result for that version jump.

The badge uses the chart's default values, not yours. To check your own values, run stageproof check -f or the pull request check.

{
  "extends": ["github>stageproof/renovate-presets"]
}

02 Why green lint still breaks production

Helm never compares the old release with the new one.

helm lint and helm template inspect the new chart in isolation. Real outages happen in the diff between what is running and what you are about to apply.

Valueshelm.values.silently_dropped

Your production override stops working

The chart renames or drops a values key. Helm silently ignores your old key with exit 0, and your setting disappears on deploy.

Upgradek8s.apply.immutable_field

A fresh install passes, the upgrade fails

Changed Deployment selectors, immutable Job pod templates, StatefulSet claim templates, or deleted PVCs fail when applied over a running release.

APIs & Imagesk8s.api.removed

Removed APIs, broken CRDs, missing tags

Stageproof checks every object against a real local Kubernetes API server, diffs CRD schemas, and verifies new container image tags exist.

No install needed: the chart index

Stageproof checks 300 popular public Helm charts every night, more than 21,000 version jumps on Kubernetes 1.35. Open a chart to see what an upgrade breaks, or paste your values.yaml to check it in your browser.

03 What one binary checks

Everything ships in v0.5.2. Free and local.

Every check below runs inside the same binary. Pass --offline to skip registry lookups, or --api-server off for an offline table-only check.

04 Results

Four clear verdicts. Three exit codes.

Any CI job that fails on a non-zero exit code already knows what to do.

PROVENexit 0

All file checks passed, and a temporary kind cluster installed, upgraded, and rolled back cleanly.

PASSEDexit 0

All checks passed. No live cluster was started (the report notes checked: files or API server).

BLOCKEDexit 1

A breaking change was found. The report names the exact rule, object, and reason. CI fails.

NOT CHECKEDexit 2

The check could not finish (bad flag, unreachable repo, or --require-rehearsal without kind). CI fails.

05 Simple & honest

Free to run everywhere. Clear about what it does.

100% free & open source

Licensed under Apache-2.0. The CLI, GitHub Action, GitLab CI component, Helm plugin, Renovate preset, and chart index are free, with no seat limits, no accounts, and no telemetry.

Your cluster stays untouched

Everything runs on your laptop or CI runner. Charts and values never leave your machine, no AI model is called, and production clusters are never modified. Even --live only creates and deletes a local temporary kind cluster.

Focused on Kubernetes upgrades

Built for Helm charts, Argo CD Applications, Flux HelmReleases, and rendered manifests (--before / --after). It does not check Terraform providers, container image internals, Kustomize directly, or language packages.
